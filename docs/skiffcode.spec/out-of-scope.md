# 범위 밖

[목차](../skiffcode.spec.md)

원격 데몬, LSP 서버 자동 설치, 키/keyboard-interactive 인증, 분할 pane,
git 커밋/스테이징 같은 쓰기 작업, 로컬 프로젝트.

**데몬을 다시 꺼내는 조건.** 데몬이 exec보다 실제로 나은 것은 아래 셋뿐이다(2026-09-18 분석).
서술로는 판정할 수 없으니 **M6에서 실기기로 재고 그 수치를 여기에 적는다.** 임계값은 실측 전에
정하지 않는다. 데몬으로 가게 되면 그때 전제는 사용자당 에이전트 하나다.

| 데몬이 이기는 것 | M6에서 잴 것 |
|---|---|
| 네트워크가 바뀌어도 LSP가 살아남는다 (가장 큰 명분, exec로는 대체 없음) | 와이파이↔LTE 전환 후 재접속부터 진단이 다시 뜰 때까지 걸린 시간, 그중 서버 재인덱싱이 차지하는 몫 |
| inotify 파일 감시 | 열린 파일 N개일 때 2초 폴링이 쓰는 왕복 수와 배터리, N이 늘 때의 기울기 |
| 트리 탐색 왕복 감소 | 프로젝트 트리를 펼칠 때 디렉터리당 SFTP `ls` 왕복 시간 |

**첫째 줄의 실측**(2026-10-06, 폴드8, 원격 Ubuntu 서버의 실제 파이썬 프로젝트와 pyright, 48줄 파일 하나의 버퍼에만
오류 한 줄). 15회의 중앙값(최소–최대), 초. 시작점은 백그라운드에서 돌아온 순간 10회(와이파이→LTE 3, LTE→와이파이 2,
와이파이 재접속 5)와, 앱을 보는 중 와이파이가 꺼진 뒤의 첫 입력 5회다. 끝점은 페이지가 진단을 받아 적용한 때다.

| 구간 | 초 |
|---|---|
| SSH 재접속 | 1.60 (1.32–1.83) |
| 옛 서버 `kill`(고아 정리) | 0.47 (0.34–0.58) |
| 언어 서버 시작(PID를 받기까지) | 0.39 (0.22–0.48) |
| `initialize` 응답 | 0.26 (0.23–0.32) |
| 첫 진단 | 0.61 (0.55–0.67) |
| **합계** | **3.37 (2.80–3.63)** |

- **재인덱싱 몫**(`initialize` 응답 + 첫 진단)은 0.87초, 합계의 약 26%다. 서버 시작까지 서버 쪽으로 치면 1.26초(37%).
  데몬이어도 SSH 재접속 1.6초는 남는다. 없어지는 것은 그 뒤의 약 1.7초(`kill`부터 첫 진단까지)다.
- 작은 파일 하나의 수치다. pyright는 열린 파일을 분석하므로, 큰 파일이나 무거운 import에서는 진단 몫이 커질 수 있다(재지 않았다).
- 끊김은 늦게 알아채지 않았다. 앱을 보는 중 와이파이를 끄면 0.24–0.27초 만에 Android가 소켓을 끊었고
  (`Software caused connection abort`), 백그라운드에서는 6초 뒤에 끊는다(`devices.md`). **LTE 위의 연결은 와이파이를
  켜도 끊기지 않았다** — 연결은 LTE에 그대로 남는다. 앱을 보는 중에 끊기면 페이지는 다음 입력이나 물음까지 서버를
  다시 띄우지 않으므로(`lspPolicy`의 `disconnected`), 그동안은 옛 진단이 그대로 보인다.
- exec 안에서 줄일 수 있는 것: 옛 서버 `kill`(0.47초)이 새 서버 시작 앞을 막고 있었다. 새 서버가 뜬 뒤 나란히 하도록
  고쳤다(2026-10-06 사용자 결정, [LSP](lsp.md)의 `LspManager`).
- **판정: exec를 유지한다**(2026-10-06 사용자 결정, [정한 것](decisions.md) 2).
